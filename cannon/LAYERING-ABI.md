# MIUI14 AArch64 layering compatibility

The official HWC ELF's DrmDevice::queryValidLayer() at 0xd69a0 and 0xd69d4
issues ioctl **0xc0806445**. It reads hrt_num at byte 84 afterwards. The
working 4.14 header independently gives a 128-byte outer structure with
three displays, and 60-byte layer entries. These values were checked with
Clang 13 targeting AArch64 in device-cannon/test67/working-abi-layout.c.
The 6.12 structure has four displays, additional fields and 72-byte layers.
Copying the old request directly into it produced `invalid layer num -1`;
the vendor handler then returned success despite failing the calculation.
HWC repeatedly crashed in setupHwcLayers+444.

Under CONFIG_CANNON_BRINGUP, the DRM file ioctl wrapper recognizes only that
exact legacy command. Other requests keep the existing drm_ioctl path. The
legacy request goes through drm_ioctl_kernel with the same AUTH/RENDER_ALLOW
flags as the native layering ioctl, retaining unplug and permission checks.
The adapter builds the native outer structure and translates nested layers
from/to the working layout. It calls the actual 6.12 layering rule and returns
its computed GLES range, OVL assignment, HRT weight and index. Copy failures
and calculation failures return errors. Native layer allocation/copy error
paths now release partially allocated state and propagate copy-back errors.

The first supported legacy case is the main display with at most 64 input
layers. Unported external display jobs and MML layer requests return
EOPNOTSUPP. Old MML frame pointers are not dereferenced; ordinary jobs receive
zeroed native MML metadata. buffer_alloc_id has no old equivalent and is zero;
the GPU cache helper is already disabled. This is not a legacy 32-bit adapter.
Native requests remain separate.

test67 validated an actual HWC HRT request: layers=1, ret=0, hrt_idx=1 at
39.447128 seconds. Its initial HWC PID remained 440, without the earlier
setupHwcLayers crash. A standard GET_CAP request and all six error probes
passed on the phone (device-cannon/test67/negative-probe-result.txt).
The two logged HRT errors at 52.066 seconds were intentionally generated by
the fault/MML probes. The next real frame was rejected separately by core
format checking: AB30 with modifier 0x0a00000000000001. The present fence
remained pending. This test does not establish visible output.

# Preceding display fixes

test65 installed a real initial mode (BOOT-MODE.md) but enabled ESD checking
before the external TE path was ready. A failure at 6.492265 seconds caused
panel resets, followed by WAIT EVENT 410 timeouts. Event 410 agrees with the
working MT6853 header. test66 selected the J22 0a panel's existing DCS health
check, 0x0A expecting 0x9C, while keeping ESD enabled. It also supplied the
correct MT6853 DSI_SHADOW_DEBUG offset 0x190 instead of the generic 0xc00
fallback. test66 retained scanning RDMA coordinates at 74 seconds and its
saved runtime had no ESD recovery failures or WAIT EVENT 410 timeouts.
